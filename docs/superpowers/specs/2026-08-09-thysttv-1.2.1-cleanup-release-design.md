## 7TV Emote-Set Compatibility

Reimplement the relevant behavior from Xtra commit `9c47305f8` in ThystTV's current Hilt-era repository and chat asset-loading architecture. This is a substantial compatibility change, not a literal cherry-pick: do not import upstream's dependency, version, service, package-name, or unrelated refactor changes.

The 7TV `/v3/users/twitch/{channelId}` response model accepts both forms used by the API:

- an embedded nullable `emote_set` object;
- a nullable `emote_set_id` that requires a second request to `/v3/emote-sets/{setId}`.

The repository first parses the user response. If the embedded set produces at least one valid emote, it preserves the current single-request behavior and returns the first nonblank ID from `embeddedSet.id?.takeIf { it.isNotBlank() }` and `emoteSetId?.takeIf { it.isNotBlank() }`. If the embedded set is absent or parses to an empty emote list and a nonblank `emote_set_id` exists, it loads `/v3/emote-sets/{setId}` through the same selected network backend and parses it with the existing WebP/GIF/PNG rules. The fallback returns the fetched set ID when nonblank and otherwise the requested set ID. Missing/empty embedded data plus a missing or blank set ID produces an empty channel-emote result without crashing. Global 7TV behavior remains unchanged.

All current consumers receive the same `Pair<setId, emotes>` contract so chat, floating chat, stream downloads, and VOD downloads continue to share one behavior. Network failures remain isolated by the consumers' existing error handling; the repository does not silently substitute global emotes for channel emotes.

Malformed individual emote entries continue to be skipped by the existing parser. Completely malformed JSON continues through the existing exception/error-handling path and is not silently converted into an empty successful response.

Tests use serialized response fixtures to cover a non-empty embedded set, an embedded set with its own ID and no top-level set ID, a blank embedded ID with a nonblank top-level ID, an empty embedded set with ID fallback, an ID-only response, missing data, all-blank IDs, malformed individual emotes, malformed JSON, and the exact fallback endpoint. A fake HTTP layer or extracted request/parse boundary proves that the second request occurs only when the embedded result is absent or empty and a nonblank fallback ID exists.

## Video-Download Segment Boundary

Reimplement the semantic change from Xtra commit `8a8b99c5b`; do not import its Gradle wrapper, dependency, JVM, package-name, or version changes. Upstream changed one loop, but current ThystTV uses `VideoDownloadWorker` and repeats the derived range across three output paths. This is therefore a moderate shared-selection refactor followed by a narrow boundary correction.

First extract the existing `relativeStartTimes`/`durations` range calculation into a small internal pure function and make all three `VideoDownloadWorker` output paths consume the same result without changing behavior. Then apply the corrected overlap rule: for millisecond inputs, return an explicit empty selection when `from >= to`; otherwise select a segment when its end is greater than `from` and its start is less than `to`. This includes a segment when `from` falls inside it while excluding a segment whose end is exactly `from`.

The function returns inclusive start/end indexes, the selected segment range, the beginning of the first selected segment as `sourceStartPosition`, the sum of whole selected segment durations, and the selected segment count. It preserves the current float-to-millisecond conversion and does not clip durations to the requested timestamps. `VideoDownloadWorker` uses the result without changing playlist downloading, URI mutation, resume progress, storage, or network behavior.

Characterization tests first prove that the extraction preserves current behavior at all three consumers. Boundary tests then cover a start inside the first segment, a start exactly on a segment boundary, an end inside a segment, `from == to`, `from > to`, an empty playlist, and a range beyond the playlist. The overlapping-start regression is observed failing against the extracted old algorithm before the corrected implementation is accepted.

## Offline Bookmarks Refresh Resilience

The logged-in Bookmarks screen refreshes locally stored VOD metadata through Helix. In the current implementation, `BookmarksViewModel.updateVideos()` launches that request without the exception isolation already used by the adjacent user and single-video refresh paths. A normal offline transport failure therefore escapes the main coroutine and can terminate the application before the user reaches locally available Saved/Downloads content.

Extract the chunk-loading and one-shot completion state into a small internal `BookmarkVideoRefreshGate`. It loads video IDs in chunks of 100, returns successfully loaded items, and marks itself complete only after every chunk succeeds. A non-cancellation exception stops the current network attempt, returns any items from earlier successful chunks, leaves the gate incomplete, and permits the next `updateVideos()` invocation to retry. `CancellationException` is always rethrown so lifecycle cancellation is never converted into an offline success. An empty ID list is a successful completed refresh, and calls after a completed refresh do not repeat the network request.

`BookmarksViewModel` keeps rendering its Room-backed flow regardless of refresh outcome and applies returned metadata using its existing update and thumbnail behavior. It does not add a new error banner, retry loop, connectivity observer, or repository-wide exception policy. Focused coroutine tests prove chunking, success suppression, retry after failure, partial-result preservation, empty input, and cancellation propagation without parsing production source. Manual branch and signed-RC smoke tests cover a logged-in account with at least one bookmark: after a cold start in airplane mode, Saved opens without crashing, local bookmarks remain visible, and Downloads remains reachable; reconnecting and reopening retries metadata refresh.

## Release Workflow and Signing Hardening

The workflow implements build-once promotion with two structurally separate modes:

- `workflow_dispatch` on post-merge `master` requires an `expected_rc_sha` input, fails unless `github.sha` equals that value, then produces the only officially signed APK that may be approved and published for that SHA. It uploads an immutable release-candidate bundle but cannot create a tag or GitHub release.
- a pushed `v*` tag does not rebuild the signed APK. Its annotated message identifies the approved signed-RC workflow run ID and manifest SHA-256. The workflow downloads that exact run's named release-candidate bundle, independently re-verifies every binding below, and publishes those exact APK and checksum bytes only when the pre-existing tag peels to the approved RC SHA.

The RC job uses `contents: read`; the tag verification job additionally receives `actions: read` only to locate and download the prior run's artifact. Only the tag-only publication job receives `contents: write`. The publication condition explicitly requires a tag-push event, and `gh release create` uses `--verify-tag` so GitHub CLI cannot create a missing tag automatically. GitHub documents that `workflow_dispatch` must exist on the default branch and can be run against a selected branch, so signed RC verification happens only after the release PR is merged to `master`.

Every external GitHub Action in the release workflow is pinned to a verified full-length immutable commit SHA. A trailing comment records the human-readable action release, with Dependabot or an equivalent deliberate maintenance process used for updates. This applies to first-party as well as third-party actions because any action in the signing job receives the job's effective access.

The signed-RC mode:

1. Fails closed unless `expected_rc_sha == github.sha`, the run is on `master`, all four signing secrets—`KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, and `KEY_PASSWORD`—are present, and release notes are complete.
2. Reads `versionName` and `versionCode`; requires `docs/release-notes/{version}.md`; and rejects placeholder release notes.
3. Runs unit tests and `lintDebug` before making key material available on disk.
4. Decodes the keystore immediately before `assembleRelease`, registers transformed sensitive material for masking where applicable, installs fail-safe cleanup before the build attempt, builds once with the configured release keystore, and removes `release-keystore.jks` immediately when the build step exits, whether it succeeds or fails and before later artifact verification runs.
5. Verifies the APK's package ID, version name, version code, and signing-certificate SHA-256 from the built artifact rather than trusting source-file text alone. The certificate digest must exactly equal a separately pinned official ThystTV release-certificate SHA-256 value; a different but cryptographically valid signing key fails.
6. Renames the APK, generates `ThystTV-{version}.apk.sha256`, and verifies the checksum.
7. Generates a machine-readable immutable manifest containing at least repository, workflow name and run ID, `rc_sha`, version name, version code, APK filename, APK SHA-256, package ID, and signing-certificate SHA-256, then calculates and records the manifest's own SHA-256 for later tag binding.
8. Uploads the APK, checksum, and manifest together as a uniquely named `{rc_sha}-{run_id}` retained workflow artifact with overwrite disabled and retention long enough to complete approval and publication. It records package, version, certificate, APK checksum, manifest checksum, run, artifact name, and verification instructions in the workflow summary.

The tag-promotion mode:

1. Requires a pushed pre-existing annotated `v{versionName}` tag whose message contains exactly one `RC-Workflow-Run` and one `RC-Manifest-SHA256` field. It verifies that the remote tag already exists, resolves the annotated tag object and peeled commit explicitly, and later uses `gh release create --verify-tag`; if project policy also requires cryptographically signed Git tags, it additionally verifies that signature against the pinned maintainer key.
2. Uses the GitHub Actions API to fetch the exact run ID named by the tag, then requires that run to belong to the release workflow, have event `workflow_dispatch`, conclusion `success`, and `head_sha` equal to the peeled tag target. It downloads that run's uniquely named artifact and fails on an invalid run, expiry, filename mismatch, or missing bundle member.
3. Treats the downloaded artifact as untrusted input until it has rechecked the checksum file and tag-recorded manifest SHA-256, recalculated the APK SHA-256, inspected package/version/version-code metadata, compared the certificate digest to both the manifest and the pinned official certificate, and matched repository, version, code, filenames, run ID, and RC SHA to the peeled tag target.
4. May rerun source-only tests, lint, and static workflow checks for defense in depth, but never invokes `assembleRelease`, re-signs, or substitutes another APK. If exact-byte promotion cannot be proved, publication stops and a new RC must be produced and approved.
5. Publishes the exact downloaded APK and checksum bytes. The manifest is retained as release evidence and may also be attached to the GitHub release.

Immediately before creating `v1.2.1`, repository policy must contain an active tag ruleset named `Protect release tags` targeting `refs/tags/v*`, with deletion and non-fast-forward updates blocked and no bypass actors. The ruleset deliberately does not restrict creation: the maintainer must still be able to create the first approved annotated tag. Once created, a matching release tag cannot be moved or deleted through normal repository permissions. The release stops if the ruleset is absent, inactive, targets the wrong pattern, lacks either protection, or grants a bypass.

Gradle no longer falls back to the debug keystore for `release`. It creates and assigns the release signing configuration only when the decoded keystore file and all three credential environment values (`KEYSTORE_PASSWORD`, `KEY_ALIAS`, and `KEY_PASSWORD`) are present. Otherwise it leaves `release.signingConfig` unset—never assigned to an empty signing config—so local `assembleRelease` produces the Android-default unsigned release APK. Local release assembly is therefore a minify/package smoke test, while the manually dispatched signed-RC workflow provides the exact certificate/package/version/checksum evidence used for release approval and later promotion. Android's build documentation confirms that a release APK is unsigned by default when no signing configuration is supplied.

The workflow receives a static structural validation test for event guards, least-privilege permissions, full-SHA action pins, the required RC-SHA input/comparison, required secrets, delayed keystore decoding and cleanup, tag/version comparison, manifest/run/SHA binding, exact-artifact promotion without a release rebuild, artifact metadata verification, pinned-certificate verification, checksum creation, uploaded assets, `--verify-tag`, and the no-placeholder-notes rule. Static assertions are not treated as execution proof: a successful post-merge verification-only `workflow_dispatch` run whose recorded head SHA equals the RC SHA and whose bundle is independently verified is an acceptance criterion. The release process document mirrors these automated gates and includes artifact download, updater, installation, and post-publication checks.

## Release-Candidate State Machine

The release lifecycle is:

1. Complete the implementation branch, ordinary code review, and branch CI.
2. Merge the release PR to `master` without creating a release tag.
3. Freeze the resulting `master` merge commit as the RC SHA.
4. Manually dispatch the verification-only signed workflow from `master` with the frozen SHA as `expected_rc_sha`; require the resulting run's head SHA and immutable bundle manifest `rc_sha` to equal it.
5. Download and independently verify the manifest-bound signed APK and checksum; record the workflow run ID and artifact name; complete manual smoke QA against that APK.
6. Run the mandatory GPT-5.6-sol/high web review and the independent GLM 5.2 or labeled fallback review against the RC SHA, full diff, workflow, notes, and verification evidence.
7. If any finding changes code, documentation, metadata, or workflow, land it through a narrow follow-up PR, freeze the new `master` SHA, and restart steps 4–6.
8. Recheck upstream and record the current head/classification.
9. Create or verify the active no-bypass `Protect release tags` ruleset for `refs/tags/v*`; then create the annotated tag exactly once.
9. Create and push annotated `v1.2.1` manually at the exact approved RC SHA, recording the approved `RC-Workflow-Run` and `RC-Manifest-SHA256` in its message. Sign the Git tag too if the project's published tag policy and maintainer key are configured before this release.
10. The tag workflow locates the successful recorded RC run, independently re-verifies its manifest and exact artifact bytes against the tag, may rerun non-artifact source gates, verifies the pre-existing tag with `--verify-tag`, and publishes the approved APK and checksum without rebuilding or re-signing them.

`workflow_dispatch` is structurally incapable of publishing. A tag workflow is structurally incapable of publishing a tag it did not receive. Moving or recreating `v1.2.1` is prohibited.

## Adversarial Review Gate

Tagging and publication are prohibited until both review lanes have been attempted on the exact post-merge `master` RC diff and signed verification evidence.

### Mandatory ChatGPT web review

Use an authenticated ChatGPT web session with GPT-5.6-sol and high reasoning. Provide the base/head SHAs, full diff, test results, release workflow, release notes, upstream source SHAs, signed-RC evidence, and explicit instructions to search for correctness, security, signing, release, lifecycle, compatibility, and regression risks. Model identity and reasoning setting are recorded in the release PR. Preserve the raw transcript or a dated attributed export/attachment; a maintainer-written summary alone does not satisfy the gate. If GPT-5.6-sol/high is unavailable, release work stops for user direction; it is not silently substituted.

### Best-effort GLM 5.2 review

Attempt an independent GLM 5.2 review through a local subagent or external crew harness after confirming the worker's actual model identity. The reviewer receives an isolated snapshot and the same adversarial scope, without the first review's conclusions. Preserve its raw output or a dated attributed export/attachment. If GLM 5.2 cannot be reached, record the failed availability check and use one available independent external reviewer only as a clearly labeled fallback. The fallback does not masquerade as GLM.

### Finding disposition

Deduplicate both review reports, verify every material claim against the repository, reject false positives with evidence, and fix each verified in-scope issue through a narrow follow-up PR. The release record contains a table with reviewer, finding, severity, verification, disposition, commit, and retest evidence. Once the RC SHA is frozen, raw transcripts, dispositions, run IDs, manifests, and verification records live out of tree as merged-PR comments/body attachments, GitHub review records, or workflow artifacts; they are not committed after the freeze because doing so would create a new RC and an endless self-invalidating evidence loop. After all fixes, rerun the full automated and manual gates. Any code, documentation, metadata, or workflow change invalidates the RC SHA and requires both review lanes to rerun under their original semantics on the new final diff before tagging.

## Error Handling and Rollback

- 7TV responses with no usable embedded emotes and no nonblank set ID produce an empty result; transport or malformed-JSON errors remain visible to existing consumer error handling and do not crash chat or downloads.
- The download selection helper returns an explicit empty selection for `from >= to`, empty playlists, and wholly out-of-playlist ranges and never reports a fabricated start position.
- An offline Bookmarks metadata refresh never terminates the app, never suppresses a later retry, never swallows coroutine cancellation, and never prevents Room-backed bookmarks or Downloads navigation from remaining usable.
- The signed-RC workflow fails before artifact approval on missing inputs, mismatched metadata, signing mismatch, test/lint/build failure, missing notes, package/version mismatch, certificate mismatch, checksum failure, or manifest-generation failure, and it removes decoded key material when the build attempt exits.
- The tag workflow fails before publication on a missing, expired, unsuccessful, or invalid tag-recorded RC run; a missing or inconsistent manifest; any SHA/run/tag/version/package/certificate/checksum mismatch; or any attempt to rebuild or substitute the APK.
- The website retains source image fallbacks and a releases-page download path that remains stable across versions.
- If a post-publication blocker is found, do not move or recreate `v1.2.1`. Mark the release affected, prepare a new version/code pair, and publish a new tag after the same review gates.
